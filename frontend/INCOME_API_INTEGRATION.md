Income API integration
======================

The existing Income, Income Report, and Income Categories layouts and styles are retained.

Connected operations
--------------------

- GET /api/Income: loads the transaction list and report. Search, date/type/payment/status filters, pagination, and CSV export operate on the returned records.
- GET /api/Income/{id}: fetches full details before viewing or editing. List responses do not contain enough fields to populate an edit form safely.
- POST /api/Income, PUT /api/Income/{id}, DELETE /api/Income/{id}: save and delete through the API, then reload the list. Failed requests do not fall back to local demo data. Repeated submissions are blocked while a request is pending.
- GET /api/Income/categories: populates the Income Type selector and category master table from the same IDs and names.
- GET /api/Farmers: supplies farmer suggestions. The form submits farmerId rather than a free-text farmer name. Duplicate names can be distinguished by ID. Existing farmer IDs survive edits even if the lookup fails.

Mapping details
---------------

IncomeListDto.date becomes incomeDate, amount becomes netAmount, and bankOrCash becomes the form's bankCash. The backend's Paid status is displayed as Received in the existing UI. An unchanged backend status and transaction timestamp are preserved when editing unrelated fields. Income numbers and gross/net totals are generated by the backend; the existing form calculates a preview from quantity, rate, discount, and other charges.

The report excludes cancelled entries. Realized income includes Received/Paid records; pending records remain in the report table and average transaction calculation.

Missing backend support
-----------------------

1. Category creation, editing, and deletion need category POST, PUT, and DELETE endpoints. The current API supports GET only. The existing category form and action buttons explain this limitation and never save browser-only changes.
2. The category response currently contains only id and name. The existing Code, Income Source, Description, and Status columns require corresponding fields. They display a dash when unavailable; active/inactive totals are unavailable rather than inferred.
3. The report's profit card needs an expense list/total or a profit summary API for the same reporting scope. No expense endpoint is present in the inspected Swagger document. The card displays a dash instead of assuming expenses are zero. A separate income-report endpoint is unnecessary while GET /api/Income returns all reportable records; server pagination would require full export and aggregate support.

Configuration and validation
----------------------------

Optional VITE_INCOME_API_URL selects the income host. It defaults to VITE_DASHBOARD_API_URL, matching the verified Swagger host. Development uses a dedicated /api/Income Vite proxy, so the authentication host in VITE_API_BASE_URL does not accidentally receive Income requests. Restart Vite after changing environment variables. The existing shared API client attaches the session access token.

The Swagger schema and live read-only list, detail, and category responses were inspected. Service tests use mocked HTTP responses, and browser checks use mocked requests. No live income records were created, changed, or deleted during verification.

Run the service/report checks with: node tests/income-api.test.mjs
